Planning and review prompts

The prompts for the architect, the three adversaries and the judge who planned Phase 1, and for the verifiers and the adversary who checked the results.

Phase 1 was planned adversarially. An architect agent drafted the plan. Three adversary agents attacked it in parallel, and none could read the others’ critiques. The architect answered every point over two rounds. A judge who took no part in the debate ruled on what was left and froze the pre-registration before any data were scored. The second-round exchanges are not among the extracted prompts.

After the results came in, a verifier reran each gate from a clean checkout and checked every number in the reports, and a methodology adversary reviewed the reports for overclaiming.

How the prompts were edited is explained on the catalog page. Terms are defined in the glossary.

Required sections:
1. Questions and hypotheses, each with a falsification criterion (what result means "fail"), primary vs secondary vs exploratory status, and the single pre-specified primary analysis for each (avoid forking paths / multiple comparisons; say how secondary analyses are corrected or labeled).
2. Operational definitions with formulas: segmentation into passages; in-context surprisal (mean bits/token given all earlier passages); cold surprisal; cold-minus-in-context; ablation payoff (window definition in passages and/or tokens, raw sum of extra bits, per-token variant); "descendants"; copy correction (exact rule: token- or word-level n-grams, n range, what "rare" means and how it is measured, what "first introduced in j" means, discount factor), reporting raw and corrected; quadrant mapping (how thresholds are set — e.g., calibrated on unplanted passages — and pre-registered); ablation sampling policy (most-surprising-first + random sample of the rest, sizes); exchange scoring (model-turn confidence, reaction surprisal, disagreement detection).
3. Planted-signal benchmark: base records (which public sources, how many, length, license), synthetic records if any; the six plant types with exact construction recipes, expected quadrant, positions and lengths (controlled/balanced), how "novel" facts are sourced (must postdate the cutoff of every model used for that test; beware scheduled events whose only novel part is the outcome) and verified absent from training data (infini-gram counts), how "known" content is verified present, how later passages use novel facts "in paraphrase, never verbatim" and how you prevent dependencies being solvable by lexical overlap alone; the confusion matrix, AUROC contrasts (seminal vs noise; seminal vs novel-inert), copy-correction effect size; sample sizes with a power/precision argument for AUROC.
4. Baselines: raw in-context surprisal, cold surprisal, zlib-normalized surprisal, Min-K% (and Min-K%++ if feasible), embedding-distance novelty, an off-the-shelf quality classifier — exact definitions and how each is turned into a score for each contrast. Consider whether cheap "forward relatedness" baselines (lexical or embedding similarity between passage j and its following window) are needed to show the method adds value beyond "later text is about the same thing".
5. Validation ladder (H1): units (records or segments; how many; sizes), the three pre-registered target kinds (later part of same record stream; related later public document(s) such as the paper a project produced; QA probes from planted post-cutoff facts), size-matched control of ordinary published text, LoRA configuration (model, ranks, target modules, steps, LR), seeds per condition, the exact definition of fine-tuning gain, the single primary cheap score and its aggregation from passages to units, Spearman with bootstrap CIs, the pre-registered test that the method beats the best baseline "clearly", and a power analysis for n units.
6. Scale tests (S1): models (≥3 sizes in one family + ≥1 other family; exact HF ids and pinned shas from FACTS_models.md; dtypes), Kendall's tau on passage and record rankings, smoothness across scale.
7. Gaming tests (G-series): placeholders are fine at this stage, but include at least the brief's four (text from a stronger model, structured gibberish, paraphrase loops, setups that make later text trivially predictable) with construction recipes and what result counts as "robust".
8. Exchange scoring stretch (X1) incl. the replay test with a newer model; note that OASST assistant turns are human-written (FACTS_data §D).
9. Cost per 10,000 tokens (S2): how measured (GPU-seconds and $ per 10k tokens for each scoring component and model size).
10. Stages and compute budget: a table of stages (smoke test → planted benchmark on small model → gate → baselines → ladder → scale → gaming → exchange stretch), each with inputs, outputs, GPU type, estimated GPU-hours and $ (use RunPod prices in ENVIRONMENT.md), and the gate/stopping rule that must pass before the next stage. The brief requires: stop and report if the planted benchmark misses its thresholds; do not run the ladder on a score that fails known answers.
11. TEE-ready packaging plan (offline container for dstack; weights mounted read-only; records from a mounted input dir; outputs = scores/maps/aggregates only; raw text never in logs/outputs except an explicit local debug mode; how this is tested). Do not analyze the TEE trust model.
12. Designs for later H2 (leading researchers' records harder to substitute) and H3 (expert disagreement grows more valuable as models improve): what Phase 1 must log or build so these can be tested later, without testing them now.
13. Risks (R-series) and threats to validity you already see.

## Lead's technical notes (considerations, not mandates — accept or reject with reasons in the plan)
1. Per FACTS_models §5, vLLM never reads the prefix cache for requests asking for prompt log-probs, so the efficient engine is HF transformers with explicit KV-cache prefix reuse (crop/copy the cache at the start of passage j, feed the window). bf16 numerical noise can reach 0.3–0.5 nats/token between cached and uncached paths, so compute the "full" and "ablated" window log-probs through the same cached code path (e.g. prefix cache [0:start_j] + [p_j + window] vs prefix cache + [window]) and do log-softmax in fp32.
2. OLMo 2 context is 4,096 tokens; size records/units to fit or specify a sliding-window scheme.
3. Seminal vs novel-inert differ by construction in whether later text relates to the plant — any relatedness measure might separate them. Decide how the plan shows the method adds value beyond that (e.g. forward-relatedness baselines; contrasts like seminal vs coined-name, where both have overlap but only one carries an idea).
4. "Most" coined-name false positives removed and "clearly above the best baseline" need operational, pre-registered definitions.
5. Power: a Spearman correlation at n=60 has a 95% CI of roughly ±0.25; comparing dependent correlations needs larger n or a paired bootstrap of the difference. Choose n for the ladder accordingly — LoRA runs on a ~1B model are cheap.
6. Novel facts must postdate every model used in the novel-plant tests (OLMo 2: Dec 2023; OLMo 3: Dec 2024; Qwen3: unstated, released Apr 2025) → 2026 facts are safest; verify absence with infini-gram (OLMo 2 data is fully indexed at api.infini-gram.io; Llama-2 tokenizer; query caps).
7. Keep scope achievable in one long working session plus background GPU jobs (one lead + builder agents). Prefer thin vertical slices and an early decisive planted-signal gate. Total RunPod spend ≤ $150.

## Style
Markdown, numbered sections, tables where they help. Be concrete (numbers, ids, formulas). Aim for roughly 450–800 lines; no filler. Mark anything you are unsure about as an open question for the adversaries/Judge. End PLAN.md with a list of open questions.

When done, reply with a 12-line summary of the plan's key choices (sample sizes, models, primary score, primary analyses, budget). Stay available: you will later receive the adversaries' critiques and must answer every point.
