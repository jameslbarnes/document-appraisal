Phase 1c pilot prompts

The prompts for the five workstreams that followed Phase 1b and for the anticipation and Navier–Stokes pilots, each run by one agent in its own git worktree under a hard spend cap.

Phase 1b closed at NO-GO on 2026-10-20: the cheap score did not predict what a model learns. At James’s request, five workstreams then started in parallel (104 to 108). Each ran as one agent in its own git worktree with a hard spend cap, and handed back a report, a branch and a list of files to merge. Two pilots followed the same day (113 and 114).

The prompts share a pattern: background with the latest numbers, a concrete task, data paths, a spend cap, privacy and git rules, and a final message that lists results, spend, branch and files to merge. How the prompts were edited is explained on the catalog page.

104 · WS1: is the score a novelty highlighter?#

Launched 2026-10-20 17:30 UTC, in its own git worktree. What it did. Asked whether the per-passage score points to the paragraph that holds a new finding, using the Phase 1b test documents, one A40 lane and a reading rule fixed before the run. What it produced. planning/HIGHLIGHTER_REPORT.md and numbers under runs/phase1c/highlight/. The answer was no. The score mostly highlighted a document’s opening setup passages; it ranked the planted finding first in 11.7% of documents, against 4.1% by chance. Spend $0.52. See the briefing.

You are working on James Barnes's compression-progress appraisal study (main repo <repo>, branch master; you are in your own git worktree created from master HEAD). Task: VALIDATE THE SCORE AS A NOVELTY HIGHLIGHTER — does the per-passage score flag the paragraph that contains a genuinely new finding?

Background (from today's Phase 1b results): the score ablates each passage j of a document (explicit KV-cache prefix ablation) and measures P_corr = the copy-corrected drop in later-text predictability when p_j is removed (CR3-B copy mask), plus S_in (bits/token of p_j in context) and S_cold (p_j alone). In the planted gate on 60 fresh test items, OLMo-2-1124-13B gave the planted "seminal" finding more P_corr than a same-story control (NI-s) in 95% of items. H1b (unit score vs LoRA gain) FAILED (rho 0.28), so the score's best remaining use may be LOCALIZATION: "which parts of my document are new to the model". That was never tested (the pre-registered S3 maps test never ran).

Data (gitignored, read from the MAIN tree by absolute path, read-only): <repo>/data/phase1b/interim/planted/variants_valid.jsonl (fields: variant_id, item_id, cluster_id, split, variant in {seminal, NI-s, NI-u, noise, known}, passages, plant_index, ...), and the sealed 13B planted outputs <repo>/runs/phase1b/sealed13/planted_test/ (planted.json, arrays.npz). First check whether jobs planted ablated ALL passages or only the plant passage (read src/cpappraise/jobs.py job_planted). If per-passage scores for every passage are not available, score the 60 test seminal variants (and their 60 NI-s twins) as units with exhaustive ablation: build a units JSONL in your worktree (unit_id = variant_id, source/set fields as jobs units needs, passages = the variant's passages) and run `python -m cpappraise.jobs units --model olmo2-13b --rule CR3-B --in <your jsonl> --out runs/phase1c/highlight/...` on a RunPod GPU via scripts/lane.py (write a lane config named configs/lane_1c_highlight.json, lane name "1C-HL", gpu "NVIDIA A40", fallbacks via scripts/lane_patient.sh; ref HEAD of YOUR worktree, so commit your scripts first; disk 150; est_hours ~1). Read scripts/lane.py and scripts/lane_patient.sh first. HARD SPEND CAP $5 (A40 is $0.59/h).

Metrics: for each seminal variant, rank of the plant passage among all its passages under (a) P_corr, (b) a surprise x payoff combination (e.g., the quadrant rule in src/cpappraise/quadrant.py with the 13B theta runs/P2/theta/theta.json in the main tree, and/or rank-product of S_cold and P_corr), (c) baselines: S_cold alone, S_in alone, per-passage in-context gain K = S_cold - S_in, and chance (1/n_passages). Report top-1 accuracy, top-3, mean reciprocal rank with cluster-bootstrap CIs (clusters = cluster_id, B=10,000, seed 20261018), and false-highlight rates on the NI-s twins (does any passage get flagged as seminal when no finding is present?). 105 · WS2: a direct-measurement appraisal protocol#

Launched 2026-10-20 17:30 UTC, in its own git worktree. What it did. Designed and prototyped the direct method as a protocol that could run inside a trusted execution environment: a fine-tune on the artifact, matched controls, comparables, a tiered panel, a bounded numbers-only report, and a threat model for extraction through the panel. What it produced. planning/APPRAISAL_PROTOCOL.md, src/cpappraise/appraise_direct.py, scripts/appraise_direct.py and 25 CPU tests, plus a demo on public stand-ins with OLMo-2-1B: recall +0.78 bits per probe, at the 100th percentile of 8 comparables. Its red team showed that per-item outputs would leak, which is why the report has none. Spend $0.62.

You are working on James Barnes's compression-progress appraisal study (main repo <repo>, master; you are in your own git worktree from master HEAD). Task: DESIGN AND PROTOTYPE A DIRECT-MEASUREMENT APPRAISAL PROTOCOL that could run inside a trusted execution environment (TEE).

Context. Member groups that represent researchers want to offer a confidential appraisal of one artifact (a research journal, agent log, dataset, method archive, record of failed experiments) inside a TEE, with bounded outputs (no raw text leaves). Today's Phase 1b result: cheap model-internal scores do NOT reliably predict what a model learns from a document (our compression-progress score rho 0.28; best cheap baseline, in-context gain, 0.44; RHO-style excess loss ~0 for a 13B with a 32B reference). Conclusion: measure directly. The repo already has the machinery: src/cpappraise/finetune.py (LoRA on OLMo-2, one sequence per step, seeds, controls by source from Wikipedia 20231101, gains G^m = mean surprisal drop on target tokens, kind-C fact probes with answer bits, merge/GoldStandard, numbers-only outputs via cpappraise.privacy), and lanes for RunPod (scripts/lane.py). Read finetune.py's module docstring and the kind-C probe code before designing.

Protocol to specify and prototype: input = an artifact (one or more documents) + a buyer-supplied panel with tiers: (1) recall probes (question/answer pairs about the artifact's content; answer bits before vs after), (2) transfer text (held-out documents in the field from other sources; bits/token before vs after), (3) side-effect text (unrelated; should not worsen), optionally (4) task items. Procedure: short LoRA fine-tune of a reference model on the artifact (with optional augmentation = rewrites), several seeds, MATCHED CONTROLS (a control artifact of similar length/domain trained the same way, so gains are net of "any training"), and COMPARABLES (run the same panel on a reference library of artifacts to report percentiles). Output: a bounded, numbers-only report per tier with seed spread and net-of-control effects. Also write the TEE threat model: what runs inside (artifact, weights, panel), what leaves, and especially PANEL-BASED EXTRACTION (a malicious buyer can craft probes like "the secret constant is 42" and read the answer-bit drop to learn private content) — propose mitigations (panel review/approval by the member, minimum aggregation sizes, reporting tier aggregates only, rate limits, noise/DP, no per-probe outputs), plus adapter destruction and audit.

Prototype: implement it as a new module or script (e.g., src/cpappraise/appraise_direct.py + scripts/appraise_direct.py) reusing finetune.py (do NOT modify frozen modules' behavior; add new code), with CPU unit tests using the tiny-model fixtures in tests/test_finetune.py (fresh_cli / _tiny_model / _pilot_units patterns): verify net-of-control gains, tier aggregation, numbers-only output, and that per-probe values are not emitted. Optional GPU demo on a public stand-in (e.g., a few ladder units from <repo>/data/interim/units/ladder.jsonl with a small synthetic panel) on an A40 via scripts/lane.py, lane name "1C-AP", HARD SPEND CAP $5; skip the GPU demo if the CPU prototype is enough to show the protocol works.

Rules: numbers and hashed ids only in outputs (privacy.write_json); never print or keep raw text in outputs. Never print secrets (your API key is loaded from an env file; never printed). If your GPU account is shared, only touch pods you created. If you stop a lane, make sure its child processes stop too (on Windows, stopping a background task can leave bash children running), and terminate your own pod. Commit in your worktree with explicit paths (`git commit -m "..." -- <paths>`), message ending with a blank line then "Co-Authored-By: Claude Opus 5.5 <noreply email>"; no git add -A, no push/merge. What it produced. planning/ANTICIPATION_DESIGN.md and data/manifests/postcutoff_candidates.json: 135 papers with at least one later citing paper (314 pairs), corrected training cutoffs (use 2025-01-01 for OLMo 2), and a recommended pilot.

114 · The Navier–Stokes pilot#

Launched 2026-10-20 19:56 UTC, in its own git worktree. What it did. What it produced. planning/NS_PILOT_REPORT.md and numbers under runs/phase1c/ns_pilot/. After one pass the two models’ profiles matched: the rank correlation across 13 related documents was 0.98. After four passes DeepSeek nearly memorized the paper, and its gain on related work became a loss. Spend: Tinker $13.97 (estimate), RunPod $0.82. See the briefing.

You are working on James Barnes's appraisal project (main repo <repo>, master; you are in your own git worktree from master HEAD).
