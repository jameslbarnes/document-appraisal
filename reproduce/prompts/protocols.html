Item and probe protocols

The frozen protocols that agents followed when writing recall and belief probes, multiple-choice behavior items, and fact records from abstracts.

Some agents did not get a one-off prompt. They followed a frozen protocol file from the repository’s prompts/ folder, named in their prompt. Three are reproduced here, each frozen before it was used: the probe protocol before any main-experiment test output, the item protocol together with the behavior test’s items, and the extraction protocol at Phase 1’s first code freeze (FZ1). The only edit is to one command in the item protocol: its absolute path is replaced with <repo>, and a wrapper that lowered CPU priority on the study machine is dropped.

Recall and belief probes (main experiment)#

Used by the main experiment’s probe writers, Claude subagents that each took a list of papers. Produced 360 recall probes (12 per paper) and the paraphrased belief probes. The build added 481 verbatim cloze probes cut from the claim sentences, for 746 belief probes in all. Writers never wrote false statements: the altered values came from a script. To reuse it with the direct protocol, note that route A needs at least 16 recall probes per document by default (see the runbook). File: prompts/main_exp_probe_protocol.md.

# Main experiment (1C-MX): probe-writing protocol (frozen before any test output)

Writers are Claude Code subagents of the 1C-MX agent. Each writer gets a list of items. For every item it reads two
local files (gitignored; never quote them anywhere else):

- `data/interim/main_exp/a_text/<item_id>.txt`: the paper A exactly as it is trained (title, abstract, sections);
- `data/interim/main_exp/claims_for_writers/<item_id>.json`: A's key claims, each with its id, kind (number or
  comparative), the true string as written in A, its counterfactual string (made by a script) and the A sentence it
  comes from.

and writes one file `data/interim/main_exp/probes_written/<item_id>.json`:

```json
{"item_id": "...", "recall": [{"prompt": "...", "answer": "...", "kind": "verbatim"}, ...],
 "belief": [{"claim": "k0", "prompt": "..."}, ...]}
```

Containment: the probes are questions about real, public papers. They contain no invented claims. The
counterfactual strings are produced by a deterministic script and attached to the belief probes by the build; writers
never write false statements about the papers. All files stay in gitignored `data/interim/`.

## Recall probes (12 per item)

- 5 **verbatim**: the prompt is an exact span of A's text (at least 8 words, copied character for character) that is
  immediately followed in A by the answer.
- 7 **paraphrase**: the prompt is in the writer's own words and names the paper ("In the paper '<title>', ..." or
  "According to <title>, ..."); it ends right before the answer.
- Answers: 1 to 5 words that occur in A (case may differ); specific to this paper (the name of its method, model,
  dataset, benchmark, component, coined term, or a key qualitative finding); not guessable from general knowledge.
- Never: numbers, years or digits in the answer; comparative words (higher, lower, better, worse, larger, smaller,
  faster, slower, stronger, weaker, best, worst, increase(s), decrease(s), improve(s), degrade(s), outperform(s),
  underperform(s), superior, inferior, advantage(s), ...) in the answer; the same answer or prompt twice; two probes
  about the same fact.
- Spread the probes over the paper (abstract, introduction, method, results, discussion).
- The prompt ends without a trailing space; the answer has no leading space (the build adds one).

## Belief probes (paraphrased cloze, one per key claim, at most 10 per item)

For each key claim listed (take the claims in the listed order, skipping any you cannot phrase well, at most 10):

- Write a prompt in your own words that names the paper ("According to <title>, ...", "In <title>, the authors
  report that ...") and ends right before the claim's string, so that the true string and the counterfactual string
  are both grammatical continuations. Do not copy the anchor sentence.
- Number claims: the prompt ends right before the number ("... reaches a success rate of"); the true string is the
  number exactly as listed (the build appends it, and the counterfactual one, with a leading space).
- Comparative claims: the prompt ends right before the comparative word ("... the proposed tokenizer trains"), so that
  "faster" and "slower" (or the listed pair) both fit.
- One prompt per claim id; no prompt may contain the claim's true or counterfactual string.

Multiple-choice behavior items (behavior test)#

Used by the behavior test’s item writers, who never saw the Navier–Stokes paper itself. A separate agent and a CPU helper checked every item. Produced the frozen item sets: 70 next-step, 30 result, 30 computation and 24 unrelated-math items. File: prompts/ns_behavior_item_protocol.md.

# NS behaviour experiment (1C-NSB): item-writing protocol

Frozen with the items (planning/NS_BEHAVIOR_PREREG.md). Item texts never leave the gitignored
`data/interim/ns_behavior/`.

## Purpose

We train a language model on one paper (the "artifact": a 2026 paper constructing finite-time blow-up for a fluid
equation) and ask whether that changes how the model approaches *related* problems. You write multiple-choice items
from related papers that apply the same kind of blow-up construction to other equations (Euler, Boussinesq, IPM),
from standard PDE knowledge, and from an unrelated area of mathematics (control items). Each item is scored without a
judge: the model's log-probability of each option given the context. A good item is one where a reader who
understands the paper's method would prefer the true option, while a reader who does not could reasonably prefer a
distractor.

## Hard rules

1. **Sources.** Read only the files you are assigned under `data/interim/ns_behavior/sources/` and your own knowledge
   of standard textbooks. Never open anything under `data/interim/ns_pilot/`, `data/raw/`, `runs/`, or any file whose
   name contains `openai`, `navier`, `ns_pilot`, `inputs.json`, `docs.jsonl` or `probes.json`. The artifact must not
   influence the items.
2. **No text leaves the gitignored area.** Write items only to the JSON file you are told
   (`data/interim/ns_behavior/items/raw/<writer>.json`). Do not paste paper text into commit messages, reports or any
   other file.
3. **Do not run models or spend money.** Use only the checker helper below (CPU, local).

## Item format (one JSON list per writer)

```json
{
  "id": "abe-ns-01",
  "set": "next_step",
  "source": "ab_euler",
  "decision_type": "amplification",
  "anchor": "exact text copied from the source that ends right before the step",
  "options": ["...", "...", "...", "..."],
  "answer": 2,
  "rationale": "why the true option is the paper's step; for each distractor, why it is sensible but not what the paper does",
  "evidence": "a short quote (<= 25 words) from the text right after the anchor that confirms the true option"
}
```

- `set`: `next_step`, `result`, `computation` or `unrelated`.
- `decision_type` (next_step and unrelated): `ansatz`, `scaling`, `amplification`, `estimate_next`, `closing`,
  `parameters`, `other`. For `result`: `quantity`, `rate`, `regularity`, `conclusion`, `other`. For `computation`:
  `scaling_exponent`, `critical_space`, `conserved_quantity`, `blowup_rate`, `criterion`, `other`.
- `answer`: the index (0-3) of the true option. Spread the true index roughly evenly over 0-3 across your items.
- `computation` items have a `question` field instead of `source`/`anchor` (see below) and a `verify` field naming
  the verification script.

## The context the model sees

For paper items (`next_step`, `result`, `unrelated`) the model sees the source text that **ends at the end of your
anchor**, trimmed from the left at a sentence start to at most 600 OLMo tokens (about 1,500-2,500 characters of
mathematical text). Then one space, then the option. So:

- The anchor must be copied **exactly** from the source file (whitespace differences are tolerated; nothing else),
  must occur **exactly once** in it, and must end at a sentence end (".", ":" or the end of a displayed formula line)
  immediately before the paper takes the step.
- Each option is written as the paper's **next sentence (or two)** at that point, so that context + " " + option
  reads as a continuation of the paper.
- Everything the model needs must lie in the ~600 tokens before the anchor end. Choose decision points where the
  preceding text sets up the choice. Run the helper with `--verbose` to see exactly where the context starts.
- The context must **not give the answer away**: no sentence in the context announces or states the step (e.g. a
  roadmap sentence "we next estimate the pressure Hessian" right before), and for `result` items the result must not
  appear earlier in the context (e.g. in an abstract that falls inside the window). Prefer decision points inside the
  body of the construction or proof, not in the abstract or introduction.

## Next-step items (`next_step`, and `unrelated` from the control papers)

A decision point is a place in a construction or proof where the authors make a substantive choice, such as:
the ansatz or form of the next correction; the scaling or the choice of scales and parameters; the mechanism that
amplifies or transfers growth; what to estimate or control next; how to close the argument (bootstrap, induction,
contradiction, summability, limiting argument).

- **True option**: a faithful, condensed statement (15-35 OLMo tokens; hard limit 40) of what the paper actually does
  next, in the paper's own notation and register. You may reuse the paper's next sentence if it is short and
  self-contained; otherwise condense it. It must be specific enough to be distinguishable from the distractors.
- **Three distractors**: steps a competent analyst could sensibly take at that point, but which the paper does **not**
  take. They must be mathematically sensible (not false on their face, not contradicting the context), not equivalent
  to the true step, not implied by it, and not something the paper also does at that point. Good families:
  a different ansatz (self-similar profile, Fourier or normal-mode truncation, explicit shear or vortex profile);
  a different mechanism (vortex stretching by an imposed strain, compactness and rescaling to a limit profile, energy
  concentration, a monotonicity or virial argument); a different estimate (energy or Sobolev estimate with Gronwall,
  maximum principle, Beale-Kato-Majda type criterion, a Lyapunov functional); different parameter or scale choices;
  a different way to close (contradiction, fixed point, continuation criterion, compactness).
- **Matching**: all four options in the same notation, register and level of specificity, with lengths within about
  25% of each other (characters). Do not let the true option be systematically the longest, the most hedged or the
  most technical. Avoid tell-tale words that only distractors use ("simply", "trivially", "never", "always") and
  avoid copying long verbatim stretches of the source into the true option while the distractors are paraphrases;
  write all four in the same style.
- Write formulas the way they appear in the source text (it is flattened PDF text: `∥∇u(t)∥L∞`, `R3`, `τ1/2`). Use
  the same flattened style in all four options.

## Result items (`result`)

The context ends right before the paper states a result or quantity it establishes (a lemma, proposition or theorem
statement, a computed rate, exponent, bound, regularity class, or conclusion). The true option is that result; the
distractors are alternative results of the same type and form (a different exponent or rate, a different regularity
class, a different quantity blowing up or staying bounded, a different conclusion) that a reader could find
plausible. Same matching rules.

## Computation items (`computation`)

Checkable multiple-choice questions on PDEs related to the artifact's area (incompressible Navier-Stokes and Euler,
Boussinesq, SQG and generalized SQG, IPM, MHD, Burgers, nonlinear heat or Schrodinger equations as model problems):
scaling exponents of self-similar ansatze, critical Lebesgue and Sobolev spaces, scaling of forces and of conserved
or controlling quantities, blow-up rates of model equations, Prodi-Serrin and Beale-Kato-Majda type criteria, energy
identities. Draw on standard texts (Majda-Bertozzi, Lemarie-Rieusset, Robinson-Rodrigo-Sadowski, Tao's notes), not
on any 2026 paper.

- `question`: a self-contained question ending with a newline and `Answer:`, e.g.
  `"Question: For ... which exponent ... ?\nAnswer:"`.
- `options`: four short answers of the same form (all exponents, or all spaces, or all expressions); exactly one
  correct; the others are the typical mistakes (wrong dimension, wrong sign, off by one power).
- `verify`: the file name of a Python script in `data/interim/ns_behavior/items/verify/` that derives the answer key
  from first principles (SymPy where possible: solve for the exponents that make the equation invariant, compute the
  critical index, differentiate the energy) and asserts that it equals `options[answer]`, and that no distractor also
  satisfies the check. Run every script; report any that fail.

## The checker helper

```
<repo>/.venv/Scripts/python.exe -I scripts/ns_behavior/prep.py check-file data/interim/ns_behavior/items/raw/<writer>.json --verbose
```

(run from the worktree root). It reports, per item: schema errors, whether the anchor is unique, the context the
model will see (token count, start and end), and option token counts and length differences. Fix every ERROR. Treat
the notes (length differences, true option longest) as things to fix unless there is a good reason.

## Deliverable

Your JSON file, passing the helper with no errors, and a short report: counts per set and decision type, the true
index distribution, and any items you are unsure about.

Fact records from abstracts (Phases 1 and 1b)#

Used by the extractors on the extraction page. Produced the fact records behind the planted test items: 245 records from 801 abstracts in Phase 1. It is a good template for any task where an agent must pull structured, quote-checked facts out of text. File: prompts/extraction.md.

# Extraction template: abstracts to fact records

Batch type `extraction`. Role: extractor (a Claude Code subagent; the model name is logged per batch). Frozen at FZ1.
Used in F1 for the novel-fact pool (arXiv v1 2026-04-01 to 2026-10-15), the K-spec pool (arXiv 2019–2022) and, only at
fallback step 3, Wikipedia 2026 science items (PREREGISTRATION §4; PLAN v3 §3.4).

You turn each input item (one arXiv abstract, or one Wikipedia event line) into at most one **fact record**: a single
numeric finding with its context, in the exact format below, or you skip the item with a reason. Code validates every
record against the shared schema (`src/cpappraise/facts/schema.py`) and checks every quote against the input text, so
follow the format literally.

## Input
Read the batch file named in your instructions. It is JSON with `batch_id`, `output_path`, `pool` (`novel`, `kspec` or
`wikipedia`) and `items`. Each item has `item_id`, `fact_id` (use it unchanged), `source` (`arxiv` or `wikipedia`),
`arxiv_id` (null for Wikipedia), `v1_date`, `domain` (null for Wikipedia items), `title` and `text` (the abstract, or the
Wikipedia line).

## Choosing the finding
Pick the single most central **numeric finding** of the item that meets every rule below. If none does, skip the item.
1. **A result, not a design choice.** A measured or computed outcome (a level, rate, share, count, duration, size,
   score or ratio that the work found). Never a sample size, number of simulations, parameter setting, threshold or
   anything else the authors chose.
2. **One number.** The value is one plain number, written in the text, with any attached symbols ("73%", "0.85",
   "1,234", "2.5-fold", "$3.2", "-0.42"). Ranges ("3 to 5"), "±" pairs, products, scientific notation and values
   written only in words are not eligible.
3. **A slot type.**
   - `quantity`: an unbounded positive amount. `unit` is its unit or the counted noun ("days", "km", "patients",
     "species", "fold", "USD"), never a percent.
   - `proportion`: a bounded value. `unit` is `"%"` if it is written as a percentage (0 < v < 100), `"fraction"` if it is
     written as a number in (0, 1) (shares, AUROC, accuracy, F1, R², probabilities), or `"r"` for a correlation
     coefficient in (−1, 1).
4. **Not directional or signed.** Skip a value that is stated as a change in some direction ("a 12% decrease",
   "reduced by 3.1 points", "increased by 40%", "+3.1", "improved from 0.71 to 0.85"), unless the text also states the
   resulting level as one number, which you may use instead ("reached an accuracy of 0.85"). A negative value is allowed
   only for a correlation (`unit` = `"r"`).
5. **At least four same-story details.** The text must support four or more further details of the same work (setting,
   subject, method, data, secondary observations) that do not state, bound or imply the value, and do not state what
   follows from it.

## The record
All text fields are single lines, in plain English, without LaTeX (write symbols in words or Unicode).
- `fact_id`: copied from the item. `arxiv_id`, `v1_date`: copied from the item.
- `domain`: copied from the item. Wikipedia items only: choose the closest of `R-BOE` (ecology, evolution, population
  biology, statistics), `R-OWW` (molecular and cell biology, biochemistry, genomics), `R-UCH` (chemistry, soft matter,
  materials) and `R-EAF` (economics, society, policy, computing and society); skip with `no_domain` if none fits.
- `entity`: the specific subject of the finding, a short noun phrase copied exactly from the text (a species, compound,
  method, model, site, cohort, mission, dataset ...). It must be specific enough to identify this work (not "the model"
  or "participants") and must not contain the value.
- `slot_value_text`: the value copied exactly from the text (character for character), as in rule 2. No separate unit
  word.
- `slot_value`: the number in `slot_value_text`, as a JSON number (73 for "73%", 1234 for "1,234", 0.85 for "0.85").
- `unit` and `slot_type`: as in rule 3.
- `f_sentence`: one sentence, in your own words, that states the finding on its own: the entity, what was measured, and
  `slot_value_text` exactly once, followed by its unit where one applies. One sentence by the study's splitter: end it
  with a period and put no other sentence-ending punctuation inside.
- `cloze_prefix`: the beginning of a sentence that describes the entity and states the claim up to the value, so that
  the value comes next ("Kidneys from gene-edited pigs kept two baboons alive for up to"). It must not contain the value
  or any other number that gives it away, and it must not end with a space.
- `consequence`: one line saying what follows from the finding, as the text states it, or its most direct implication
  that the text supports. Nothing speculative.
- `details`: four to six details of the same work (rule 5), each one sentence in your own words, standalone (no "this"
  or "it" pointing to another sentence), distinct from each other and from `f_sentence`, and each free of the value.
- `new_name`: `true` if the work introduces a new name (a newly described species, compound, method, model, mission or
  dataset name), else `false`. `name_term`: that new name, copied exactly from the text, if `new_name` is true; else
  `null`.

## Support quotes (checked by code)
For every record, also give exact quotes from the item's `text`, copied character for character:
- `slot_quote`: 6–20 consecutive words that contain `slot_value_text`; it must occur exactly once in `text`;
- `detail_quotes`: one quote per detail, in the same order, 3–30 words each, each occurring exactly once in `text`, that
  supports that detail.
Code also checks that `entity` and `name_term` occur in the item's `title` or `text` exactly as written.

## Skips
Skip an item, with one reason, when no finding meets the rules: `no_numeric_finding`, `design_value_only`,
`directional_or_signed`, `two_numbers`, `fewer_than_4_details`, `no_domain` (Wikipedia only), `unreadable` (for
example, mostly formulas). Do not lower the bar to avoid a skip; most items are expected to be skipped.

## Output schema
```json
{
  "schema": "cpa.authoring.output/1",
  "batch_id": "<copied from the batch file>",
  "model": "<the model name you are running as>",
  "items": [
    {
      "item_id": "<copied>",
      "status": "record",
      "record": {
        "fact_id": "<copied>", "arxiv_id": "<copied>", "domain": "<copied or chosen>", "v1_date": "<copied>",
        "entity": "<exact noun phrase>", "slot_value_text": "<exact value>", "slot_value": 0.0,
        "unit": "<unit>", "slot_type": "quantity", "f_sentence": "<one sentence>",
        "cloze_prefix": "<prefix>", "consequence": "<one line>",
        "details": ["<detail>", "<detail>", "<detail>", "<detail>"],
        "new_name": false, "name_term": null
      },
      "support": {"slot_quote": "<exact quote>", "detail_quotes": ["<q1>", "<q2>", "<q3>", "<q4>"]}
    },
    {"item_id": "<copied>", "status": "skip", "skip_reason": "directional_or_signed"}
  ]
}
```
The record must have exactly these fifteen keys, no others.

## Check your file before you reply (if you can run shell commands)
From the repository root, run one of:
- PowerShell: `$env:PYTHONPATH = "src"; .venv\Scripts\python.exe -m cpappraise.authoring selfcheck <batch file> <output file>`
- bash: `PYTHONPATH=src .venv/Scripts/python.exe -m cpappraise.authoring selfcheck <batch file> <output file>`

It prints one line per item: `OK`, `SKIP` or failure codes (it never prints texts). Fix every failure and run it again,
at most four times in all. A failing record may be fixed or turned into a skip, never forced through by changing the
facts.

## Output and reply
- Write one JSON file to the batch's `output_path` (UTF-8, LF line endings) with exactly the schema above: one entry per
  input item, in input order, with `item_id` copied exactly. Do not create or edit any other file.
- Reply with one status line and nothing else: `OK <batch_id> <records> records <skips> skips`, or
  `FAIL <batch_id> <short reason>`. Never put any of the texts in your reply.
