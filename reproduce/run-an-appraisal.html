Run an appraisal of a public document

A step-by-step runbook for measuring what one public document teaches OLMo-2-13B, and optionally DeepSeek-V3.1, with the study's existing code, from gathering inputs to reading the results.

Research code, not a tool

This is the code that ran the study. There is no one-command appraisal yet. You assemble input files, write a lane config, run several scripts and read JSON output. Two of the three routes below were written for one experiment and must be adapted by editing code. The study’s probes and test items were written by AI agents (Claude subagents) under frozen protocols. You will need to write or commission your own, and agent-written probes are a known limit of the study.

What you will measure#

An appraisal is a controlled comparison (see the method). You train one copy of a model on your document and another copy on a control document of the same length. Both copies get the same steps, the same number of tokens and the same random seeds. Then you score both copies, and the untrained base model, on the same panel of tests. The document’s gain over the base, minus the control’s gain, is what the document taught.

Three extras are optional:

  • Comparables place your result as a percentile among similar documents appraised the same way.
  • Follow-ups, later papers that cite your document, show whether it helps predict the work built on it.
  • The increment trains both copies on a background of related papers as well, so the difference shows what your document adds beyond them.

Terms such as LoRA, dose, panel, copy mask and bits are defined in the glossary.

Choose a route#

Route Models What you get What you must adapt
A. python -m cpappraise.appraise_direct OLMo-2 (1B to 13B) on RunPod One document against controls and comparables. Recall, transfer, side and task tiers. A bounded, numbers-only report with an interval, a percentile and a status per tier Write the input files and a lane config
B. scripts/ns_pilot.py OLMo-2-13B on RunPod and DeepSeek-V3.1 on Tinker One document on both models. Recall, plus related, background and side text tiers, and the open-versus-frontier comparison Edit its source table, which lists the Navier–Stokes pilot’s documents, and write a probe file
C. scripts/main_exp/ and python -m cpappraise.mainexp.run Both Several documents in blocks, with citing follow-ups. Anticipation, the increment over background papers, and the counterfactual truth arms Add your documents as items. The pipeline expects arXiv papers with later citing papers

Route A is the most general for one document on the open model. Route B is the shortest path to both models. Route C is the setup behind the main experiment’s numbers and, of the three, the only one with the increment arms built in.

Before you start#

  1. Set up the environment and accounts as in the requirements, and run the tests.
  2. Work in a fresh git worktree or branch. Routes B and C write to fixed paths under data/interim/ and runs/phase1c/, so a separate branch keeps the study’s files intact.
  3. Keep text out of git:
    • put each download in its own new directory under data/raw/, which is gitignored;
    • read downloads only with scripts run as python -I;
    • keep built inputs under data/interim/, which is also gitignored;
    • commit only numbers-only outputs, written with privacy.write_json.
  4. Commit your code before a lane runs. A lane pushes the committed state at its ref (a commit, a tag or HEAD) to the pod, plus the input files it lists.

In the commands below, python means the environment’s interpreter.

Step 1: Gather the inputs#

The document#

  • arXiv papers. The HTML rendering is the cleanest source. scripts/main_exp/fetch_html.py fetches exact versions one at a time, at least 15 seconds apart (the crawl delay in arXiv’s robots.txt), each into a new directory under data/raw/main_exp/. cpappraise.anticipation.text turns a page into passages and drops the bibliography and back matter.
  • PDFs. cpappraise.ns_pilot has pdf_text, which runs pdftotext -raw, and clean_pdf_text, which removes running heads, arXiv stamps and the references section.
  • Length. OLMo-2 reads 4,096 tokens at a time. The code splits the document into passages of about 128 tokens and groups them into training sequences: at most 2,048 tokens in the main experiment, 3,584 in the Navier–Stokes runs. The main experiment capped each paper at 24,000 tokens.

A control of the same length#

  • What it is. An unrelated document at least as long as yours, in tokens.
  • Packing. The code packs the control into your document’s training profile: the same number of sequences, with the same token lengths (appraise_direct.pack). A control that is too short is refused. So both copies get identical steps and tokens.
  • What the study used. The main experiment used papers from an unrelated field, concatenated to at least 30,000 tokens (scripts/main_exp/plan_wave2.py controls). The Navier–Stokes runs used one long algebra paper. The behavior test’s report notes that a control from the same field, on an unrelated topic, would isolate method effects better.

Comparables (optional)#

  • Similar documents, appraised with the same controls, recipe and panel. Route A reports your document’s percentile among them, in deciles, when there are at least five.
  • Each comparable costs as many runs as your document. Route A’s run count is seeds × (1 + controls + comparables), so comparables dominate the cost of a small appraisal.

Probes#

  • Recall probes are fill-in-the-blank prompts written from the document, scored by the bits of the exact answer.
  • The protocol. Follow prompts/main_exp_probe_protocol.md, shown on the protocols page:
    • 12 per document: 5 verbatim, 7 paraphrased;
    • answers of 1 to 5 words that occur in the document and are specific to it;
    • no numbers or comparative words in answers;
    • spread over the whole paper.
  • Belief probes (optional) test whether the model takes on a paper’s specific claims. Each is scored with a true and an altered answer.
  • Who writes them. The study’s probes were written by Claude subagents. Write yours yourself, or have an agent write them and check them.
  • Route A’s screen. Before it runs, Route A checks the panel without a model (screen):
    • at least 16 recall probes by default (min_items in the config);
    • no answer or prompt used more than twice;
    • at most 10% near-duplicates;
    • at most 25% numeric answers, unless the approval allows more.
  • Answer spacing. Route A tokenizes the prompt and the answer separately and joins the tokens. Start the answer with a space when the prompt ends without one. The main-experiment build adds this space for you.

Follow-ups, related documents and side text#

  • Follow-ups (anticipation) are later papers that cite your document. Route C finds the sentences that cite it (mainexp.cites) and scores them as their own tier.
  • Related documents (transfer) are papers in the same field by other authors. They are never trained on.
  • Side text is unrelated text, which should not change. The study used Wikipedia texts chosen by python -m cpappraise.finetune select-controls, which writes the gitignored data/interim/controls/wikipedia_20231101.jsonl.
  • The copy mask applies automatically. Tokens that a scored text copies from the training document count as zero gain, so pasting a panel text into the document earns nothing.

Background papers (for the increment)#

In the main experiment the background was three of the document’s references: arXiv papers from 2025 up to the document’s own month, not by its authors, each capped at 6,000 tokens (scripts/main_exp/plan_wave2.py background).

Step 2: Calibrate the dose for each model#

  • The dose is how hard a model fits the document: D = 1 − L_after / L_base. L is the mean bits per token over the document’s own training sequences, scored on the base model and again after training.
  • The anchor is OLMo-2-13B with LoRA at a constant learning rate of 1e-4 for one epoch. This is the light dose at which paper-specific anticipation appeared in the pilot.

  • Matching. DeepSeek-V3.1 trains for the same one epoch, on the same passage groups in the same order. Its learning rate is the knob:

    1. run two to four learning rates for one epoch with one seed, scoring only the document’s own sequences;
    2. interpolate on log-log axes between the two rates that bracket OLMo’s mean D;
    3. round to two significant digits, and never go above 1e-4.

    If OLMo’s D lies outside the range you ran, run one more rate. That was the behavior test’s rule; the main experiment’s rule took the nearest rate it had run.

  • What the study found.

    • At the same learning rate, DeepSeek fits about 2.6 times harder.
    • On the main experiment’s development papers, DeepSeek at 5.5e-5 dropped its loss on the paper by 3.8%, against OLMo’s 3.7% at 1e-4. On the 30 test papers the drops were 6.23% and 6.25%, and the per-paper drops agreed closely (Spearman 0.97).
    • For the much longer Navier–Stokes paper the matched rate was 2.9e-5, and both models’ loss on the paper fell by about 15%. So calibrate for each document set.
  • Why it matters. In the Navier–Stokes pilot, at four epochs and an unmatched dose, DeepSeek’s training loss on the paper fell to 0.18 bits per token, near memorization, and its profile diverged from OLMo’s.
  • The code.
    • Route C: python -I scripts/main_exp/calibrate.py build; the OLMo calibration lane configs/lane_1c_mx_cal.json, which scores the dose at a quarter, half, three quarters and the end of the epoch; python -I scripts/main_exp/calibrate.py tinker --lrs 1e-4 5e-5 2.5e-5 1.25e-5; then python -I scripts/main_exp/calibrate.py choose.
    • One paper: python -I scripts/ns_behavior/tinker_nsb.py calib --lrs ... and then choose, from the behavior test.
    • Both read their own experiment’s inputs. Adapt the one closer to your setup.
  • Route A uses the open model alone, so there is nothing to match. Use the same anchor, LR 1e-4 and one epoch, so your numbers are comparable with the study’s.

Step 3: Run the open model on RunPod#

Write a lane config#

A lane config lists the GPU, the disk, the git ref to push, a time estimate, the input files to push, the pinned models to download and the steps to run. Copy the closest existing config. The template below follows configs/lane_ap_demo1b_final.json and configs/lane_1c_nsb_olmo13.json. Save it as, for example, configs/lane_my_ap_1.json; my_appraisal and MY-AP-1 are placeholder names.

{
 "lane": "MY-AP-1",
 "gpu": "NVIDIA A40",
 "disk": 150,
 "ref": "HEAD",
 "est_hours": 1.0,
 "inputs": [
  "data/interim/my_appraisal/artifact.jsonl",
  "data/interim/my_appraisal/controls.jsonl",
  "data/interim/my_appraisal/comparables.jsonl",
  "data/interim/my_appraisal/panel.json",
  "data/interim/my_appraisal/config.json",
  "data/interim/my_appraisal/approval.json"
 ],
 "models": ["olmo2-13b"],
 "steps": [
  {
   "name": "appraise",
   "cmd": "PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python -m cpappraise.appraise_direct run --artifact data/interim/my_appraisal/artifact.jsonl --panel data/interim/my_appraisal/panel.json --controls data/interim/my_appraisal/controls.jsonl --comparables data/interim/my_appraisal/comparables.jsonl --approval data/interim/my_appraisal/approval.json --config data/interim/my_appraisal/config.json --out runs/my_appraisal",
   "heartbeat": "runs/my_appraisal/progress.json",
   "pull": "runs/my_appraisal",
   "pull_every_min": 15,
   "watchdog_min": 30
  }
 ]
}
  • models takes keys from cpappraise.jobs.MODELS: olmo2-1b, olmo2-7b, olmo2-13b, olmo2-32b, qwen3-1.7b, qwen3-4b. Each is pinned to a Hugging Face revision, and fetch_model.py checks every weight file’s size.
  • est_hours is logged before the run, and the pod is terminated at twice that time. Size it from the cost table in planning/APPRAISAL_PROTOCOL.md (section 8).
  • pull_every_min pulls partial outputs while a step runs, watchdog_min stops a step whose heartbeat stalls, and resume: true pushes pulled parts back before a retried step. Resume helps only jobs that skip finished parts: the Route B and C runners do, and Route A does not.

Route A: the direct protocol#

The input files:

  • artifact.jsonl: one document per line, as {"doc_id": ..., "passages": [...]}, or {"doc_id": ..., "text": ...} to let the frozen splitter cut the passages.
  • controls.jsonl and comparables.jsonl: the same lines plus "artifact_id". Lines with the same id form one artifact.
  • panel.json: {"panel_id": ..., "recall": [{"id", "prompt", "answer"}], "transfer": [{"id", "text"}], "side": [{"id", "text"}], "task": [{"id", "prompt", "choices", "correct"}]}. Any tier may be absent.
  • config.json: a partial config whose keys merge into the defaults. For the study’s light dose on the 13B: {"model": "olmo2-13b", "lr": 1e-4, "epochs": 1, "seeds": [11, 22], "gradient_checkpointing": true}. The module’s defaults (OLMo-2-1B, LR 1e-4, 8 epochs, seeds 11, 22 and 33) come from the earlier phases.

tests/test_appraise_direct.py builds small working examples of every input on CPU. In the commands below the paths are shortened; in the lane they point into data/interim/my_appraisal/.

python -m cpappraise.appraise_direct screen --artifact artifact.jsonl --panel panel.json --out screen/ --config config.json
python -m cpappraise.appraise_direct approve --artifact artifact.jsonl --panel panel.json --controls controls.jsonl --comparables comparables.jsonl --out approval.json --config config.json
python -m cpappraise.appraise_direct run --artifact artifact.jsonl --panel panel.json --controls controls.jsonl --comparables comparables.jsonl --approval approval.json --out runs/my_appraisal --config config.json
  • screen checks the panel locally, without a model.
  • approve writes an approval that binds the digests of the document, panel, recipe, controls and comparables. In a confidential appraisal the document’s owner would sign it after reviewing the panel; here you approve your own. Add --allow-numeric if more than a quarter of the answers are numbers. If any input changes, approve again.
  • run is the lane step. It trains and scores every arm and writes report.json and audit.json.

Route B: both models from one script#

  1. Edit SOURCES in scripts/ns_pilot.py: one row with the role train (your document), one control, and rows for the related, background and side documents. prep also expects the pilot’s optional second training arm (arm2) and its two Lean repositories. Remove those parts.
  2. Write data/interim/ns_pilot/probes.json as {"probes": [{"id", "kind", "prompt", "answer"}]}, where kind is verbatim, paraphrase or implication.
  3. Run python -I scripts/ns_pilot.py prep. It builds data/interim/ns_pilot/inputs.json (training arms and panel), the copy-mask flags, and a sources manifest with hashes and counts.
  4. Copy configs/lane_1c_ns_olmo13.json and change its step to one epoch, as below.
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python scripts/ns_pilot.py olmo --inputs data/interim/ns_pilot/inputs.json --out runs/phase1c/ns_pilot/olmo --seeds 11 22 --epochs 1 --eval-at 1 --lr 1e-4

Route C: blocks of papers#

The main experiment’s scripts, in order. They select items from data/manifests/postcutoff_candidates.json, so a new document enters as a candidate with its citing papers; expect to adapt plan_fetch.py and select_items.py.

python -I scripts/main_exp/plan_fetch.py --tier 1 > data/interim/main_exp/fetch_tier1.txt
python -I scripts/main_exp/fetch_html.py --list data/interim/main_exp/fetch_tier1.txt
python -I scripts/main_exp/select_items.py check
python -I scripts/main_exp/select_items.py freeze
python -I scripts/main_exp/plan_wave2.py extra-related > data/interim/main_exp/fetch_wave2.txt
python -I scripts/main_exp/plan_wave2.py controls > data/interim/main_exp/fetch_ctrl.txt
python -I scripts/main_exp/plan_wave2.py background > data/interim/main_exp/fetch_bg.txt
# fetch each of the three lists with fetch_html.py --list
python -I scripts/main_exp/build_inputs.py texts
# probe writers follow prompts/main_exp_probe_protocol.md
python -I scripts/main_exp/build_inputs.py probes
python -I scripts/main_exp/build_inputs.py blocks
python -I scripts/main_exp/cpu_smoke.py --block 1 --items 2 --seeds 11
# dose calibration (Step 2), then freeze your analysis plan and commit it
python -I scripts/main_exp/make_lanes.py --groups 1,2 3,4 5,6 --est-hours 1.9

make_lanes.py writes configs/lane_1c_mx_<k>.json with one step per block:

PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True python -m cpappraise.mainexp.run --block data/interim/main_exp/pods/block_1.olmo2-13b.json --out runs/phase1c/main_exp/olmo2-13b/block_1 --model olmo2-13b --seeds 11,22 --arms A,cfk,cfr,ctrl,bgA,bgC --lr 1e-4 --gradient-checkpointing on

For a plain appraisal without the truth arms, drop cfk and cfr from --arms. The pre-registered analysis (scripts/main_exp/analyze.py) also computes the truth contrasts from those arms, so adapt it as well.

Launch and watch a lane#

python scripts/lane.py configs/lane_my_ap_1.json
nohup bash scripts/lane_patient.sh configs/lane_my_ap_1.json runs/lanes/MY-AP-1.patient.log 120 "NVIDIA A40" "NVIDIA RTX A6000" "NVIDIA L40S" > /dev/null 2>&1 &
python scripts/runpod_pod.py list
python scripts/runpod_pod.py cost
  • Run short lanes with lane.py. Launch long ones detached through lane_patient.sh, which retries the listed GPU types every three minutes until one is free or the deadline, in minutes, passes.
  • Watch runs/lanes/<lane>.jsonl. It logs the estimate, the pushed commit, readiness, partial pulls, each finished step, and termination with the ledger’s cost.
  • Afterward, check with list that no pod of yours is left, and terminate any by id (python scripts/runpod_pod.py terminate <id>). On a shared account, do not use reap: it terminates every cpa-* pod.
  • If you stop a lane by hand, make sure its child processes stop too. On Windows, stopping a background shell can leave its children running, and one of them once created a duplicate pod.
  • The lane scripts call bash, ssh and tar. On Windows the study used Git Bash.

Step 4: Run the frontier model on Tinker#

The Tinker helpers load your API key from an env file and never print it.

Smoke test first. For Route B, python -I scripts/ns_pilot.py tinker-smoke trains and scores a few hundred tokens. It cost $0.004 in the pilot.

Route B. Run with --dry-run first to see the projected cost, then without it. The command refuses to start if the spend so far plus the projection would pass --cap.

python -I scripts/ns_pilot.py tinker --inputs data/interim/ns_pilot/inputs.json --out runs/phase1c/ns_pilot/deepseek --seeds 11 22 --epochs 1 --eval-at 1 --lr <calibrated LR> --cap <dollars> --dry-run

Route C. Run python -I scripts/main_exp/tinker_run.py --blocks 1 2 3 4 5 6 --dry-run, then the same without --dry-run. It reads the calibrated learning rate from runs/phase1c/main_exp/calib/calibration.json, checks the projection against the cap, and runs every arm in each block’s input.

Clean up. Delete the sampler checkpoints, then confirm that Tinker lists none:

  • Route B: python -I scripts/ns_pilot.py tinker-cleanup --ledger runs/phase1c/ns_pilot/deepseek/checkpoints.json;
  • Route C: python -I scripts/main_exp/tinker_run.py --blocks 1 --cleanup.

Billing. python -I scripts/ns_pilot.py tinker-billing (Route B) or tinker_run.py --billing 24 (Route C) reconciles the spend estimate with Tinker’s billing records, which lag by hours.

Step 5: The increment run#

  • What it measures. What your document adds beyond related work: (background + document) minus (background + control), for each panel tier.

  • How the main experiment built it. Two extra arms per item, in src/cpappraise/mainexp/build.py:

    • bgA: the background papers’ training sequences, then the document’s;
    • bgC: the same background sequences, then the control packed to the document’s profile.

    Each arm trains for one epoch over all its sequences, in a seeded order, at the calibrated learning rate. The background is token-identical in both arms, so the difference between them is the document’s contribution.

  • Run it by including the arms: --arms A,ctrl,bgA,bgC on the OLMo lane. tinker_run.py runs every arm that a block’s input contains.

  • Read it in results.json under H-D, or with scripts/main_exp/tables.py. In the main experiment:
    • recall survived the background in full: OLMo gained +1.34 bits per probe beyond the background, against +1.09 alone;
    • about half (OLMo) to two-thirds (DeepSeek) of the gain on the document’s own follow-up remained.
  • Routes A and B do not build these arms. Adding the increment there means building the two arms in code the same way.

Step 6: Outputs, and how to read them#

Where the outputs are#

  • Route A: report.json, the bounded report, and audit.json, which records code, inputs and timings, in the --out directory.
  • Route B: per-model parts under .../olmo/ and .../deepseek/. Then python -I scripts/ns_pilot.py analyze --out runs/phase1c/ns_pilot --eval-at 1 writes results.json and effects.json, and python -I scripts/ns_pilot.py tables prints the tables.
  • Route C: python -I scripts/main_exp/analyze.py writes results.json and effects.json. posthoc.py adds descriptive extras, including the dose per paper, and tables.py prints the tables.
  • Before you commit, scan the outputs for leaked text. cpappraise.privacy.scan_for_leaks looks for 8-word runs of your inputs; Route C also has scripts/main_exp/leak_scan.py.

Reading a tier#

Route A’s report gives these fields for each tier. Routes B and C report the same ideas under similar names.

  • base: the untrained model’s level, for example bits per recall answer.
  • ctrl_gain: what training on the control did. It measures the effect of any training of this size, and it can be negative.
  • net: the document’s gain minus the control’s, averaged over items and seeds. Positive means the document made the tier easier for the model.
  • ci_lo and ci_hi: an approximate interval, the net plus or minus two standard errors, combining item and seed spread.
  • pct: the percentile among comparables, in deciles. It is empty with fewer than five comparables.
  • status: gain or loss only when the interval excludes zero and the net reaches a minimum effect (0.1 bits per probe for recall, 0.002 bits per token for text). Otherwise inconclusive. A tier never reads “not learned”: inconclusive means not detected with this recipe, panel and model.

Sizes to expect#

From the main experiment (30 papers, one light dose):

  • Recall: +0.81 bits per probe net of the control for OLMo-2-13B, and +0.46 for DeepSeek-V3.1. One bit means the model became twice as likely to give the exact answer.
  • Follow-ups: the document’s own citing paper became 0.0097 (OLMo) and 0.0096 (DeepSeek) bits per token easier, about 0.4% of its base difficulty. Small numbers are normal at a light dose.
  • Side text stayed near zero. A clear loss there flags damage from the training.

Comparing models#

  • Check the achieved dose first. If the two models’ drops on the document’s own text differ, their profiles are not comparable. Route C reports the dose in results.json and posthoc.json.
  • Compare shape, not size. The two models ranked the 30 papers alike on recall, follow-ups and field transfer (rank correlations 0.68 to 0.75). But DeepSeek’s recall gains were 0.57 times OLMo’s.

Limits#

  • One light dose of LoRA. LoRA probably understates what full training would teach.
  • The probes come from agents, not from the people who would use the result.
  • The choice of control matters. The behavior test’s report suggests a same-field control.
  • The truth test on later papers’ text did not pass cleanly. In OLMo, a copy of a paper with its key claims altered made the citing sentences as predictable as the true paper did. An appraisal shows what a model learned, not whether it is true.
