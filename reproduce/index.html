Reproduce and extend

Where the code lives, what you need to rerun it, what each experiment cost, and how AI agents planned, built, checked and ran the work.

Who this is for#

This section is for readers who want to rerun the study or build on it. Everything here points to the code that actually ran the experiments, in the cp-appraisal repository. All paths below are relative to the root of that repository.

Access to the code

The cp-appraisal repository is not public yet. A cleaned copy is being prepared for release, with private material and contained test texts removed. Until then, ask James Barnes for access.

Research code

The code ran every experiment on this site, but it is not packaged as a tool. There is no one-command appraisal yet. Expect to read scripts, write small input files and edit configs. Test items and probes were written by AI agents under frozen protocols, not by independent experts.

To appraise a document of your own, go to the runbook. To reuse the agent roles, go to the agent prompts. Terms such as LoRA, dose, control, panel and copy mask are defined in the glossary.

The package: src/cpappraise/#

These modules matter most for new work. Most come from the later experiments (Phase 1c); finetune.py, copyrule.py and privacy.py date from Phase 1 and are used throughout.

Module What it does
appraise_direct.py The direct method as a protocol. It fine-tunes a pinned open model on a document with LoRA, trains matched controls the same way, optionally runs comparables, and scores a panel in four tiers (recall, transfer, side, task). It reports net-of-control tier values with intervals, percentiles and a gain, inconclusive or loss status, in a bounded numbers-only report. Command line: python -m cpappraise.appraise_direct screen, approve and run
finetune.py The LoRA trainer behind every OLMo training run: OLMo-2, rank 16 and alpha 32 on every projection, AdamW, gradient clip 1.0, one sequence per step, optional gradient checkpointing for the 13B. Also probe and text scoring, and select-controls, which picks the Wikipedia control and side texts
mainexp/ The main experiment. cites finds the sentences of a later paper that cite a paper. claims finds key claims and makes the scripted counterfactual copies. texts and build make the block inputs for both models. run is the one-epoch train-and-score loop, with an OLMo backend and a Tinker backend. stats and analysis hold the pre-registered statistics
nsbehavior/ The Navier–Stokes behavior test: multiple-choice items and the verbatim-run filter (items), the run loop (run), judge-free scoring (analysis), and open-ended strategy answers for blind grading (strategy)
ns_pilot.py The Navier–Stokes pilot: PDF text cleaning, panel windows, the copy mask mapped onto both models’ tokenizers, a Tinker backend with a spend guard, and the open-versus-frontier comparison
anticipation/ The anticipation pilot: arXiv HTML to passages (text), scripted counterfactuals (cf), blocks and masks (build), the GPU job (run) and the transfer-matrix statistics (stats)
copyrule.py The copy rule. Its fallback version, CR3-B, is the copy mask in every later experiment: words copied from the training document earn no credit
privacy.py The output guard. write_json refuses any string that is not a short, allow-listed label, so committed results hold only numbers, hashed ids and labels. scan_for_leaks checks outputs for 8-word runs of input text

The machinery of Phases 1 and 1b, the cheap score and its planted test, is in the same package. It includes engine.py (per-token log-probabilities with key-value cache reuse), jobs.py (GPU scoring jobs and the pinned model list), segment.py, score.py, payoff.py and quadrant.py. Also there: contamination.py (training-data checks through infini-gram), facts/, data/, plant/, authoring.py, evaluate.py, baselines.py, analysis/, gaming/ and fabrication.py. appraise.py, guard.py and render.py are the offline container entrypoint, with its Dockerfile in docker/.

Scripts: scripts/#

Script What it does
lane.py Runs one GPU lane on RunPod from a config. It creates a pod, pushes a committed git ref and the inputs, sets up the environment (pod_setup.sh), downloads pinned weights (fetch_model.py), runs each step under nohup, pulls the outputs and terminates the pod. Per step it supports a heartbeat watchdog, partial pulls and resume. It terminates the pod at twice the time estimate
lane_patient.sh Retries a lane across several GPU types until one is free or a deadline passes (through lane_retry.sh). Use it for long lanes, launched detached
runpod_pod.py Pod lifecycle by hand: create, wait, ssh, push-code, push, pull, terminate, list, reap, cost. Every pod is named cpa-* and logged to runs/runpod_ledger.jsonl. cost turns the ledger into dollars per stage. Caution: reap terminates every cpa-* pod in the account
main_exp/ The main experiment, in run order: plan_fetch, fetch_html, select_items, plan_wave2, build_inputs, calibrate, make_lanes, cpu_smoke, tinker_run, analyze, posthoc, tables, leak_scan, ledger_lines. tinker_common holds the Tinker helpers: service client, spend guard, checkpoint cleanup and billing
ns_behavior/ prep (items, checks, model inputs), tinker_nsb (smoke test, dose calibration, learning-rate choice, main runs, cleanup, billing), strategy_grade (blind grading packets) and analyze
ns_pilot.py The Navier–Stokes pilot end to end: prep, olmo (the pod step), tinker-smoke, tinker, analyze, tables, tinker-cleanup, tinker-billing
appraise_direct.py Demo inputs on public stand-ins, and the offline red-team analysis of the direct protocol
anticipation/ Inputs, item selection and analysis for the anticipation pilot

Configs: configs/#

  • lane_*.json: one file per lane. Each names the GPU, disk size, git ref, time estimate, inputs, models and steps. The names follow the stage:
    • lane_1c_mx_cal.json and lane_1c_mx_1.json to _3.json: main experiment (calibration, then two blocks per lane);
    • lane_1c_nsb_olmo13.json: behavior test;
    • lane_1c_ns_olmo13.json: Navier–Stokes pilot;
    • lane_1c_ant_*.json: anticipation pilot;
    • lane_1c_highlight.json: highlighter;
    • lane_ap_demo1b*.json: direct-protocol demo;
    • lane_h1b* and lane_h1bx*: the Phase 1b learning test;
    • lane_p*: Phase 1.
  • finetune_pilot.json and finetune_pilot_13b.json: the LoRA pilot grids of Phases 1 and 1b.
  • appraise.yaml: the config of the Phase 1 container entrypoint.

Tests: tests/#

There is one test file per module. Tests run offline on CPU with tiny random models, so they cost nothing. Run python -m pytest -q before any paid run. At the main experiment the full suite stood at 848 passed, 3 skipped and 1 expected failure. scripts/main_exp/cpu_smoke.py runs the whole main-experiment pipeline on tiny random models before any spend.

Planning documents and reports#

  • Phases 1 and 1b. planning/BRIEF.md (the brief), planning/PLAN.md (v3, frozen by hash), PREREGISTRATION.md, REPORT.md and SUMMARY.md; then PREREG_1B.md, REPORT_1B.md and SUMMARY_1B.md.
  • Phase 1c. In planning/: HIGHLIGHTER_REPORT.md, APPRAISAL_PROTOCOL.md, ANTICIPATION_DESIGN.md, PROCESS_VALUE_DESIGN.md, TRANSFER_DESIGN.md, ANTICIPATION_PILOT_PREREG.md and _REPORT.md, NS_PILOT_REPORT.md, MAIN_EXPERIMENT_PREREG.md and _REPORT.md, NS_BEHAVIOR_PREREG.md and _REPORT.md, and RELATED_WORK.md.
  • Checks. planning/critique_*.md (adversaries), planning/architect_response_r*.md, and planning/VERIFIER_*.md (replications and number checks).
  • Process. DECISION_LOG.md records every decision and deviation (D1 to D53, plus the judge’s rulings J1 onward). CHECKINS.md holds the check-ins with James. BUILD.md sets the rules for builder agents, and planning/BUILD_QUESTIONS.md holds their questions and the lead’s answers.

Results: runs/#

  • runs/phase1c/<experiment>/ holds results.json (every statistic), effects.json (per-item values under hashed ids), tables.md, and the spend and session files. Phases 1 and 1b are under runs/P*, runs/Q1* and runs/phase1b/.
  • runs/runpod_ledger.jsonl records every pod’s creation and termination. Per-experiment ledgers, such as runs/phase1c/main_exp/runpod_ledger_1C-MX.jsonl, were merged into it by the lead.
  • runs/lanes/<lane>.jsonl is each lane’s event log.
  • Not in git: pod state (runs/pods/), debug text (runs/**/debug/) and per-token arrays (*.npz). Raw downloads (data/raw/), caches and built inputs (data/interim/) are gitignored too, because they hold document text.

Requirements#

Python and the uv environment#

The repository is a Python package, cpappraise (Python 3.11 or later; the study used 3.12). Dependencies are pinned in requirements/base.txt and requirements/torch.txt. Build the environment with uv, as scripts/pod_setup.sh does on a pod:

uv venv --python 3.12 .venv
uv pip install --python .venv/Scripts/python.exe -r requirements/torch.txt
uv pip install --python .venv/Scripts/python.exe -r requirements/base.txt
uv pip install --python .venv/Scripts/python.exe -e . --no-deps
uv pip install --python .venv/Scripts/python.exe tinker
.venv/Scripts/python.exe -m pytest -q

On Linux or macOS the interpreter is .venv/bin/python. The Tinker client is needed only for the frontier-model runs. It is not in requirements/base.txt; the study used version 0.34.0.

Local work needs only a CPU: building inputs, tests, analysis and smoke runs. All model training and scoring runs on RunPod or Tinker. If your documents are PDFs, you also need pdftotext (Poppler), which the Navier–Stokes code uses.

RunPod, for the open model#

  • Account. You need a RunPod account with credit, your API key, and an SSH key pair for pod access. scripts/runpod_pod.py creates each pod with your public key and connects over SSH.
  • GPU. A40-class cards were the most cost-effective. An A40 has 48 GB and cost $0.59 an hour in the secure cloud at the time. OLMo-2-13B with LoRA and gradient checkpointing peaks at about 30–35 GB, so it fits. In the anticipation pilot an A40 trained about 650 tokens per second and scored about 2,150. The same 13B pilot run took 81.5 s on an A40 and 33.3 s on an H200 at $5.29 an hour: about $0.013 against $0.049 per run (DECISION_LOG.md, D47).
  • Which cards. Use 48 GB Ampere or Ada cards (A40, RTX A6000, L40S). Avoid Blackwell cards: a run on one failed with “no kernel image is available”, most likely because the setup fell back to an older PyTorch build (D43).
  • Disk and start-up. Give each pod 120–150 GB of disk, because OLMo-2-13B’s weights are 55 GB in fp32 on Hugging Face. A pod takes about 4.5 minutes to boot. With environment setup and the weight download, plan on 10–20 minutes of fixed cost per lane.

Tinker, for the frontier model#

  • What it is. Tinker, from Thinking Machines, trains LoRA adapters on hosted open-weight frontier models and returns per-token log-probabilities, which the panel scoring needs.
  • Model. The study used DeepSeek-V3.1, which was trainable with a 32,768-token context. Kimi-K2.6 was also trainable but was not used.
  • Price. The DeepSeek-V3.1 rate card at the time was $3.718 per million training tokens, $1.695 per million prefill tokens and $4.215 per million sampled tokens.
  • Recipe. LoRA rank 16 on attention and MLP projections, with no unembedding adapter. Text is scored raw, with no chat template. Panels are scored through sampling clients at the prefill rate, because forward passes on a training client bill at the training rate.
  • Practicalities.
    • Limit concurrency. The pilot’s first run fired about 190 scoring requests at once and crashed the client; one panel at a time with 12 requests in flight fixed it.
    • Tinker also throttles concurrent training clients.
    • Billing rows lag by hours.
    • Delete sampler checkpoints after use.

API keys#

Both services need an API key. The scripts load each key into the running process from the environment or an env file, and they never print or log it. No key is stored in the repository. Point the loaders at your own env file: scripts/runpod_env.py for RunPod, and the Tinker helpers in scripts/main_exp/tinker_common.py and scripts/ns_pilot.py.

Per document#

In the main-experiment setup, an appraisal costs about $1 per document for both models together, and about $0.10 for the open model alone.

  • Both models. Tinker’s main runs cost $37.06 and the OLMo lanes $2.85, for 30 papers. That is $1.33 per paper, with two counterfactual arms that a plain appraisal does not need.
  • Open model alone. $2.85 over 30 papers is about $0.10.
  • Each paper had four arms: the paper, two altered copies and a control, with two seeds each. Nine papers also had two increment arms.

How the work was run with AI agents#

The study ran over four days with Claude Code agents under James Barnes’s direction. One lead session held the plan, wrote a prompt for each subagent, launched it, read its short report, merged its work and kept the decision log. The agent prompts section publishes those prompts.

A lead session, and subagents in git worktrees#

  • Prompts. Most prompts named:
    • the files to read first, and which one was the authority (the frozen pre-registration, BUILD.md);
    • the files the agent owned;
    • the deliverables, with exact paths;
    • the hard rules;
    • what to report back, in a few lines.
  • Phase 1 builders worked in one shared working tree. BUILD.md gave each module one owner. Builders committed explicit paths only, never git add -A, so no one committed another agent’s files.
  • From Phase 1c on, each experiment ran in its own git worktree, on a branch named worktree-agent-<id>, so an agent could not disturb the main checkout or another agent. Gitignored inputs were copied in, read-only.
  • Writers and extractors wrote JSON files and replied with one status line. The lead never read texts it did not need.
  • Budgets. Every paid task had a hard spend cap. The agent estimated the cost before each paid stage and stopped and reported rather than exceed the cap.
  • Refusals. When a writer agent or a safety classifier declined a task, the lead did not reword the prompt or hand the batch to another agent. Once, the lead explained the safeguards and left the decision to the agent, which resumed (D35). Otherwise the work stopped, and the affected test was recorded as failed or not run (D23, D38).

Adversaries and a verifier#

  • Planning. Three adversaries attacked the Phase 1 plan in parallel: methodology (validity), gaming (inputs that should score high without value) and efficiency (cost). None could read the others’ critiques. The architect answered every point over two rounds. A judge who took no part in the debate ruled on what was left and froze the pre-registration.
  • Reports. A methodology adversary reviewed the Phase 1 and Phase 1b reports for overclaiming before each phase closed. On the Phase 1b report it found 7 blocking and 11 non-blocking issues, and the report was revised.
  • Verifier. A verifier re-derived the Phase 1 and Phase 1b results:
    • It reran each gate from a clean checkout, with its own bootstrap seed. Both replicated exactly.
    • It recomputed every number in each report from the result files. Phase 1 had 3 mismatches among 449 checked values; Phase 1b had 12 among 791 rows, mostly cents of spend. None changed a verdict, and all were corrected.
  • Not verified. The Phase 1c experiments, including the main experiment, had no separate verifier pass.

Frozen notes before scoring, kept light#

  • Phase 1 had a full pre-registration with staged code freezes: code for each stage was committed and tagged before that stage scored data.
  • Phase 1b sealed the two scorers’ outputs by hash until both lanes had finished (scripts/seal.py).
  • Later experiments each froze one short note, committed with the analysis code before any test output existed. This covers the anticipation pilot, the main experiment (commit 55e9ca4) and the behavior test (commit bbcdff1). James asked for this lighter form: one frozen note, no ceremony.
  • Anything decided after scoring is labeled exploratory or descriptive.

Numbers-only outputs#

  • The guard. Committed results pass through privacy.write_json: numbers, hashed ids and short labels only.
  • Text stays out of git. Document texts, probes, model answers and counterfactual copies stay in gitignored folders. The main experiment ran an 8-word leak scan over everything it was about to commit.
  • Downloads are untrusted data. Each went in its own new directory and was read only by scripts run with python -I.
  • Altered copies are contained. Copies of real papers with altered claims were made by deterministic scripts, never by a writer model. They were never committed or published.

GPU ledgers, detached jobs and cleanup#

  • Ledgers.
    • Every pod is logged at creation and termination. Worktree agents wrote their own ledger file, and the lead merged it into the tracked ledger in a separate commit.
    • On Tinker, a cumulative spend guard refuses any request that would pass the cap. A projection is checked before each stage, and session records allow billing to be reconciled later.
  • Detached long jobs.
    • Long lanes were launched detached, with nohup bash scripts/lane_patient.sh ..., because the agents’ own background tasks end after two hours.
    • Each step pulls partial outputs every 10–20 minutes, a watchdog stops a step whose heartbeat stalls, and a retried step resumes from its pulled parts. These features came from losing an unpulled pilot (D48) and from finding that the watchdog had not been running during steps (D49).
  • Cleanup.
    • Every Tinker sampler checkpoint was deleted right after its scoring, and the listing was checked to be empty.
    • Every pod was terminated.
    • The direct protocol never writes trained weights to disk. At the end it zeroes the LoRA weights, or restores the original weights after full fine-tuning.
  • Shared accounts. If your GPU account is shared, only touch pods you created.

Merging#

The lead merged each worktree branch into master with git merge --no-ff, so each experiment is one merge commit (for example “Merge 1C-MX main experiment …” and “Merge 1C-NSB …”). The lane’s ledger lines went into the tracked ledger in their own commit.
